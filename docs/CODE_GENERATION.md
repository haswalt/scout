# Code generation

Scout uses code generation for the HomeData API client, Panda CSS output, and UI
component scaffolds. Generated files have different ownership rules from
handwritten source: update their input or template, then regenerate them.

## HomeData API client

The typed HomeData client is generated by `@hey-api/openapi-ts`.

| Input                                     | Purpose                                                 |
| ----------------------------------------- | ------------------------------------------------------- |
| `packages/homedata/src/openapi-spec.yaml` | API operations and data schemas                         |
| `packages/homedata/openapi-ts.config.ts`  | Generator input, output, and plugin configuration       |
| `packages/homedata/src/config.ts`         | Runtime client configuration and API-key authentication |
| `packages/homedata/src/client`            | Generated output                                        |

To regenerate only the HomeData client:

```sh
pnpm --filter @repo/homedata codegen
```

The generator reads the local OpenAPI specification, uses the Next.js client
plugin, formats the output, and replaces files under
`packages/homedata/src/client`.

The root command also runs all configured workspace generation tasks:

```sh
pnpm codegen
```

After generation:

```sh
pnpm lint
pnpm check-types
pnpm build
git diff -- packages/homedata/src/client
```

Review the diff for unexpected removed operations or type changes, but do not
edit generated client files directly. Make corrections in the OpenAPI
specification, generator configuration, or handwritten runtime configuration
and regenerate. The client directory is committed so workspace consumers and
CI use a reproducible API surface, but it is excluded from linting and
formatting.

`HOMEDATA_API_KEY` is applied at runtime by `packages/homedata/src/config.ts`.
Never put credentials or environment-specific values in the OpenAPI
specification or generated output.

## Panda CSS output

Panda generates typed CSS utilities into `packages/ui/styled-system`. The UI
package build regenerates this directory:

```sh
pnpm --filter @repo/ui build
```

Run it after changing Scout tokens, Panda configuration, recipes, or component
style usage. `styled-system` is generated build output and must not be edited
manually.

## Creating a UI component

Use the Turborepo generator from the repository root:

```sh
pnpm generate:component
```

Enter a component name when prompted, for example `alert banner`. The generator
normalizes the name and creates:

```text
packages/ui/src/alert-banner/
  index.tsx
  index.test.tsx
  styles.ts
  types.ts
```

The templates live in `turbo/generators/templates/component`. Update those
templates when a convention should apply to every future component.

The scaffold provides a styled `div`, an empty Panda recipe, native `div` props,
a public documentation comment, and a basic semantic rendering test. Complete
the component by:

1. choosing the correct native element and matching React prop type;
2. defining recipe variants and defaults in `styles.ts`;
3. documenting behavior, variants, and accessibility expectations;
4. adding meaningful behavior and accessibility tests;
5. regenerating Panda output when new styles or recipes require it.

Package exports use the `@repo/ui/*` wildcard, so a generated `alert-banner`
component is imported as:

```tsx
import { AlertBanner } from "@repo/ui/alert-banner";
```

Before committing a new component, run:

```sh
pnpm --filter @repo/ui build
pnpm --filter @repo/ui coverage -- --run
pnpm --filter @repo/ui check-types
pnpm --filter @repo/ui lint
```

Tests should verify user-observable behavior, semantic roles, accessible names,
keyboard interaction where relevant, disabled states, prop forwarding, and
recipe variants. The UI package enforces 100% coverage, but line execution alone
is not sufficient; assertions must describe the intended contract.
